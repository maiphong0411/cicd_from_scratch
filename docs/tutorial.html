From a git commit to running software, on your own laptop

You will build a complete CI/CD pipeline locally. First you do every job by hand, so you know what it is. Then you hand the jobs to a robot.

The problem

Code on your disk is not running software. Between the two there are always the same five jobs, whatever tools you choose.

JobQuestion it answersTool in this lab
CheckDoes the code work, and is it written safely?unit tests, SonarQube
PackHow do I ship the code with everything it needs?Docker image
StoreWhere can a different machine fetch the package?registry
RunWho keeps the right version running?Kubernetes, described with Helm
AutomateWho does all of this, in order, on every commit?Jenkins

CI (continuous integration) is Check and Pack: every commit is proven to work and turned into a package. CD (continuous delivery) is Run: the package becomes the running version. The package in the registry is the handoff between them.

How to read this lab. For each tool, separate three things: a hard constraint (it cannot work any other way), a design decision (someone chose it, and paid something for it), and a convention (a habit you could change). The tools will change during your career. The five jobs will not.

Before you start

  • Install Docker Desktop, kubectl, kind and helm. Give Docker at least 8 GB of memory; the full stack uses about 4 GB.
  • Pull the large images ahead of class, because they are slow to download: kindest/node, sonarqube:community, jenkins/jenkins:lts-jdk21, registry:2, python:3.13-alpine.
  • The app is given to you: a 15-line Python web server in app/app.py and one unit test in tests/test_app.py. Your work is everything around it.

The lab, step by step

Steps 1 to 6 are done by hand. Step 7 automates them. Step 8 adds environments.

1Start

Run the app as a plain process

What has to be true for code to answer a request?

Four things: an executable the operating system can start, every file it needs, a network port it holds, and something keeping it alive. Every later tool exists to guarantee one of these on a machine that is not yours.

python3 app/app.py                          # terminal 1: leave it running
curl localhost:8000                         # terminal 2
lsof -nP -iTCP:8000 -sTCP:LISTEN

Observe. The process that owns port 8000 is Python, not app.py. Your file is only text; the interpreter is what runs. Stop it with Ctrl+C and curl is refused: a port only exists while a process holds it.

2Pack

Build a container image

Why is copying app.py to a server not enough?

The server needs the same interpreter and libraries too. An image ships them with the code: it is a packed filesystem plus a note saying which command to start. A container is an ordinary process started from an image, which the kernel shows only that filesystem and a private set of ports.

# Dockerfile
FROM python:3.13-alpine
WORKDIR /app
COPY app/app.py .
ENV PYTHONUNBUFFERED=1
USER nobody
EXPOSE 8000
CMD ["python", "app.py"]
docker build -t app:v1 .
docker run -d --name try -p 8000:8000 -e APP_VERSION=v1 app:v1
curl localhost:8000
docker exec try python --version
docker exec try ps
docker rm -f try

Observe. The image is about 45 MB for 15 lines of code: that is the price of shipping the dependencies. Inside, Python is 3.13 whatever your laptop has, and ps shows a single process.

Ask yourselfRun it again without -p 8000:8000. Why does curl fail although the app is running?
3Store

Push the image to a registry

How does an image get from the machine that builds it to the machine that runs it?

They share no disk, only the network. A registry is an HTTP server for images. The image name is also its address: localhost:5001/app:v1 means server, repository, version.

docker run -d --name registry -p 127.0.0.1:5001:5000 registry:2
docker tag app:v1 localhost:5001/app:v1
docker push localhost:5001/app:v1
curl localhost:5001/v2/app/tags/list

Rule. Never reuse a tag. A tag is only a label, and the registry will accept different content under the same one. If that happens, nobody can say which code v1 is, and rolling back to it means nothing. The pipeline will tag every image with its git commit ID.

4Run

Run it on Kubernetes

Who restarts the app when it crashes, and replaces it when a new version arrives?

You tell Kubernetes what should be true, for example "2 copies of this image". It then loops forever: look at what is running, compare with what you asked for, fix the difference. A crash and a new version are both just differences. kind gives you a real cluster inside one Docker container.

kind create cluster --name cicd --config infra/kind.yaml
docker network connect kind registry
docker exec cicd-control-plane sh -c 'mkdir -p /etc/containerd/certs.d/localhost:5001 &&
  echo "[host.\"http://registry:5000\"]" > /etc/containerd/certs.d/localhost:5001/hosts.toml'

kubectl create deployment app --image=localhost:5001/app:v1 --replicas=2
kubectl get pods
kubectl delete pod <one pod name>
kubectl get pods
kubectl create service nodeport app --tcp=80:8000 --node-port=30081
curl localhost:8081

Observe. After you delete a pod there are still two, and one has a new name. Kubernetes did not revive the old pod; it made a new one, because the stored wish still says 2.

ObjectIts jobWithout it
Deploymentkeeps the right number of pods of the right image alivenothing runs
Serviceone fixed address in front of pods whose addresses keep changingthe app runs but cannot be reached

The tricky part. localhost means "this machine" to whoever says it. On your laptop localhost:5001 is the registry; inside the cluster node it is the node itself. The hosts.toml line tells the node to fetch localhost:5001 images from the registry container instead.

5Run

Describe it in files with Helm

What you typed in step 4 is recorded nowhere. How could a robot repeat it?

Write the Deployment and Service as files. Between two releases only one value differs, the image tag, so Helm keeps the files as templates with blanks and fills them at deploy time. Each deploy is stored as a numbered revision.

kubectl delete deployment app && kubectl delete service app

helm template app chart                       # preview, changes nothing
helm upgrade --install app chart --wait
helm upgrade --install app chart --wait --set image.tag=v2
helm history app
helm rollback app 1 --wait

Observe. During the upgrade, a new pod becomes ready before an old one is removed, so the app never goes down. The rollback takes seconds: nothing is rebuilt, because the old image is still in the registry.

6Check

Tests and a SonarQube quality gate

What stops broken code before it is packed?

Two different checks. Tests run the code and ask "does it do the right thing?". Static analysis reads the code without running it and asks "is it written in a way that tends to go wrong?". Neither replaces the other.

python3 -m coverage run --source=app -m unittest discover tests
python3 -m coverage xml
echo $?                                       # 0 = success, anything else = failure

docker run -d --name sonarqube --network kind -p 127.0.0.1:9000:9000 sonarqube:community
# log in at localhost:9000, create an analysis token, then:
sonar-scanner -Dsonar.host.url=http://sonarqube:9000 -Dsonar.qualitygate.wait=true

Observe. The scan ends with QUALITY GATE STATUS: PASSED and exit code 0. The quality gate is a set of thresholds on the server. With qualitygate.wait, a failed gate becomes a non-zero exit code.

The whole mechanism of a pipeline is the exit code. A pipeline runs a command, reads that number, and stops if it is not 0.

7Automate

Hand the jobs to Jenkins

Who runs steps 2 to 6, in order, every time?

Jenkins waits for a new commit, runs a list of commands, and records the result. It adds no new ability. The list is the Jenkinsfile, stored with the code, and every line in it is a command you have already typed.

// Jenkinsfile, shortened
TAG = first 7 characters of the git commit

stage('Test')          sh 'python3 -m coverage run ... unittest discover tests'
stage('SonarQube')     sh 'sonar-scanner ... -Dsonar.qualitygate.wait=true'
stage('Build & Push')  sh 'docker build -t $IMAGE:$TAG . && docker push $IMAGE:$TAG'
stage('Deploy')        sh 'helm upgrade --install app chart --set image.tag=$TAG --wait --rollback-on-failure'
stage('Smoke test')    sh 'curl ... | grep "version $TAG"'
docker compose up -d                          # Jenkins at localhost:8080
git commit -am "Change greeting"              # then watch
curl localhost:8081

Observe. In the build's console output you will recognize every command, ending with Finished: SUCCESS. About a minute after a commit, curl answers with that commit's ID.

A robot has only the abilities you hand it. Jenkins gets the git repository, the Docker socket, the cluster credentials and the SonarQube token. That list is what Jenkins can do, and also what someone who broke into Jenkins could do.

8Environments

One pipeline, three branches, three environments

How does a change reach production in controlled steps?

Each long-lived branch deploys to its own namespace, a separate area inside the same cluster. Jenkins checks every branch each minute and builds any branch whose latest commit it has not seen. A merge is simply a new commit on the target branch, so merging is what triggers the deploy.

developnamespace develop · 1 copylocalhost:8081
uatnamespace uat · 1 copylocalhost:8082
prodnamespace prod · 2 copieslocalhost:8083
# the Deploy stage uses the branch name twice
helm upgrade --install app chart \
  --namespace $BRANCH_NAME \
  -f chart/values-$BRANCH_NAME.yaml \
  --set image.tag=$TAG
git checkout uat  && git merge develop        # promote to uat
curl localhost:8082
git checkout prod && git merge uat            # promote to prod
curl localhost:8083

Observe. After merging into uat, only port 8082 shows the new version. The same chart and the same code serve all three; the differences live in three small values files.

Break it on purpose

You understand a pipeline when you can predict how it fails. Guess the outcome before you run each one.

Do thisWhat should happen
Break the test and commitThe build fails at Test. Later stages are skipped. The running app is untouched.
Delete all podsKubernetes recreates them within seconds, with new names.
Break the start command in the Dockerfile and commitTest and scan pass, Deploy fails, Helm restores the previous revision.
Commit to develop onlyOnly the develop environment changes.
Roll back one Helm revisionThe previous version serves again in seconds, with no rebuild.

What this lab leaves out

The lab is honest about the mechanism and simplified in the surroundings. A real team would add:

  • A git server with pull requests and protected branches. Here the repository is local, and Jenkins polls it every minute instead of being notified.
  • An approval step before production.
  • Building the image once and promoting that same image, instead of rebuilding on each branch.
  • Separate build machines. Here Jenkins runs as root with the laptop's Docker socket, which is full control of the host.
  • Passwords and TLS on the registry, a real database for SonarQube, and per-branch analysis, which the free edition lacks.

Words you will hear

Image
A packed filesystem plus a start command. Does nothing until started.
Container
A process started from an image, with a restricted view of files and network.
Registry
A server that stores images so other machines can fetch them.
Tag
The version label on an image. Here, the git commit ID.
Node
A machine in a Kubernetes cluster.
Pod
A running container managed by Kubernetes. Disposable.
Deployment
The stored wish "keep N pods of this image running".
Service
A fixed address that forwards to whichever pods currently exist.
Namespace
A named, separate area inside one cluster. Here, one per environment.
Chart
Helm's templates for the Kubernetes files, with blanks.
Values
What fills the blanks. One small file per environment.
Release
One installed chart, with numbered revisions you can roll back to.
Quality gate
SonarQube's pass or fail verdict against a set of thresholds.
Stage
One step of the pipeline. A non-zero exit code stops the run.
Smoke test
A check that the deployed app answers, and with the expected version.
